# Как ведём TimberWings

## Один большой пакет — один результат

ROADMAP — центральная очередь. Мелкие действия выполняются внутри пакета и не требуют ежедневно менять документы. Когда разработчик говорит «задача готова», проверяем критерии и обновляем только затронутые документы. Одна основная подсистема/чат/ветка/PR, затем принятие; main не превращаем в место экспериментов.

## Порядок

1. Читать README, ROADMAP и документы системы. Проверить актуальный SHA и чистый git status.
2. Выбрать ID, scope, результат, зависимости; ветка fix/…, polish/…, feat/… или docs/….
3. Изучить код, сцены, связи. Реализовать только задачу. Если нужны ассеты, описать назначение/интеграцию.
4. Проверить компиляцию и релевантный QA; для дефектов билда — standalone. Отчёт: что сделано, файлы, что тестировано, что не тестировано.
5. После принятия закрыть ID в ROADMAP; актуализировать GDD/BALANCE/ARCHITECTURE/BUILD_QA только по факту; добавить запись CHANGELOG. Коммит/PR с ID.
6. Merge в main после принятия. Следующая задача начинается с актуального main. Если код готов, но тест не проведён — REVIEW, не DONE.

## Версии

Предлагается MAJOR.MINOR.PATCH для релизов; фактический номер согласовываем при STAB-06, не выводим из старой версии в меню. Patch — исправление, Minor — крупная совместимая обнова, Major — несовместимые изменения. До тега используем SHA и release candidate. Не ставить tag на непроверенный билд.

## Пример закрытия

STAB-01: после PASS в сборке ROADMAP = DONE, ARCHITECTURE уточнить pipeline карты, BUILD_QA — результат и доказательство, CHANGELOG — запись. GDD/BALANCE не менять, если правила и цифры прежние.

## Git и файлы

Git LFS для бинарных ассетов. Не коммитить Library, Temp, Logs, локальные сейвы, билды, лишние архивы. .meta сохранять вместе с ассетом. Уже отслеживаемые бэкапы не удалять без аудита. Перед push проверять diff/git status. Код и документированное изменение правил должны соответствовать одной версии.
